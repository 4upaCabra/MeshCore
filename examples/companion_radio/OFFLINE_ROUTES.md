# Офлайн-очередь и маршруты офлайн-сообщений

Пока приложение не подключено, компаньон копит сообщения в очереди. Эта схема
делает две вещи:

1. очередь переживает перезагрузку узла;
2. приложение получает **маршрут** каждого канального сообщения, как если бы
   видело эфир вживую.

| Что | Линия | Кому |
|---|---|---|
| Маршрут канального сообщения | OS и SEC (`WITH_OFFLINE_ROUTES`) | любому приложению |
| Очередь во флеше | OS и SEC | — |

Заменяет прежнюю схему с двумя независимыми кольцами (сырые кадры отдельно,
очередь отдельно); в OS та схема жила только в RAM.

## Принцип

Отдаём ровно то, что приложение увидело бы вживую, и только для своих сообщений.

- В момент, когда узел расшифровал сообщение и кладёт его в очередь, он берёт
  сырой пакет **именно этой копии** (`Packet::writeTo`, путь как пришёл — свой хэш
  узел дописывает позже, при пересылке) и хранит его вместе с сообщением.
- При отдаче (`CMD_SYNC_NEXT_MESSAGE`) этот сырой пакет уходит пушем
  `PUSH_CODE_LOG_RX_DATA` **непосредственно перед** своим сообщением.
- Только для сообщений, пришедших флудом: у прямого маршрута путь по дороге
  расходуется, показывать нечего. Хранятся только канальные полезные нагрузки
  (`PAYLOAD_TYPE_GRP_TXT`, `PAYLOAD_TYPE_GRP_DATA`).
- Маршрут хранится и тогда, когда приложение подключено: оно получило эту копию
  живым пушем, но может отключиться, не забрав сообщение. Чтобы текущий сеанс не
  получил ту же копию дважды (клиент посчитал бы её лишним повтором), у записи
  хранится номер сеанса приложения, видевшего её вживую; сеанс — это
  `CMD_APP_START`. Повторно маршрут уходит только в другом сеансе.

## Почему именно так — что делают клиенты

Проверено по коду клиентов: meshcore-open (`zjs81/meshcore-open`, `dev` @
`9334d556`) и официальное приложение — по веб-сборке
`app.meshcore.nz/main.dart.js` v1.50.0 (build 78); мобильные сборки не
разбирались.

Путь канального сообщения все клиенты берут **только** из сырого кадра
`0x88`: в кадре сообщения (`RESP_CODE_CHANNEL_MSG_RECV_V3`) есть лишь число хопов.

| Клиент | `CMD_APP_START` | Канал: кадр до сообщения | Канал: после |
|---|---|---|---|
| Официальное | `meshcore-flutter`, без `cap=` | да, если сообщение придёт в течение **3 с** | да |
| meshcore-open | `MeshCoreOpen`, без `cap=` | да | да |
| MCO Advanced | `MeshCoreOpen;cap=…` | да | да |

- **Официальное приложение.** Сырой канальный кадр сообщения строку не создаёт:
  поиск сообщения откладывается на 3 с и идёт по ключу канала, времени отправителя,
  типу и тексту, без окна по давности. Найдено — путь записывается как «услышанный
  повтор» сообщения. Поэтому кадр нужно отдавать **вплотную** к сообщению: при
  прежней схеме (сначала весь буфер кадров, потом сообщения) путь мог не
  привязаться.
- **meshcore-open** создаёт сообщение из сырого кадра сам и сливает с кадром
  сообщения по секунде, отправителю и тексту — порядок не важен.
- **MCO Advanced** сливает канальные копии по хэшу содержимого в любом порядке.
- Канальный сырой кадр плюс сообщение дают у клиентов один «повтор» — так же, как
  вживую.

## Кому отдаётся

- Канальный маршрут — любому приложению: все известные клиенты превращают его в
  путь сообщения.

В OS у офлайн-маршрутов нет кадрированных пакетов (фрагментов): сырой пакет
длиннее `MAX_FRAME_SIZE` не отправляется — как и живой пуш. Поэтому длинное
канальное сообщение (сырой пакет больше ~170 байт) останется без пути.

## Хранение

- **RAM-очередь** как была (до 256 записей). У каждой записи — порядковый номер
  (`offline_queue_seq`) и место маршрута (`offline_queue_route`: нет / в пуле RAM /
  в записи во флеше).
- **Пул маршрутов в RAM** — `OFFLINE_ROUTE_POOL_SLOTS` (6) сырых пакетов до записи
  во флеш. При переполнении теряет маршрут самая старая запись.
- **Кольцо во флеше** — `src/helpers/OfflineRecordRing.*`, по файлу на запись
  (`/oqNN.bin`) плюс индекс (`/oqidx.bin`), во второй ФС (на nRF52 это 100 КБ
  `ExtraFS`, общая с контактами).
  - Запись = кадр очереди + его маршрут, слот = `seq % OFFLINE_STORE_SLOTS`, номер
    лежит в самой записи, CRC32 по всей записи.
  - Прочитанное приложением — **водяная метка**: самый старый номер, ещё лежащий в
    RAM-очереди. Всё ниже неё отдано или выброшено намеренно. Счётчика, который
    съезжал бы при выпадении записи из середины очереди, нет.
  - При загрузке непрочитанные записи возвращаются в очередь по порядку номеров,
    со своими номерами; маршруты остаются во флеше и читаются при отдаче.
  - Старые раскладки (`/rf*.bin`, `/rq*.bin`, `/rawfeed.bin`) удаляются при старте.
- Логика кольца покрыта нативными тестами: `pio test -e native -f
  test_offline_record_ring`.

## Когда пишется флеш

- Только из `loop()`, **никогда при поднятом BLE** (`NRF52_PLATFORM` с
  `BLE_PIN_CODE`): запись во флеш останавливает SoftDevice. Обработчик запроса
  сообщений (`CMD_SYNC_NEXT_MESSAGE`) во флеш не пишет. На nRF52 USB-сборках
  проводной линк — не BLE и записи не блокирует.
- Только после паузы в очереди: 3 с без новых записей (но не дольше 15 с от самой
  старой незаписанной). Сообщение, которое приложение забрало сразу, флеш не
  трогает вовсе.
- По две записи за проход `loop()`; индекс — после паузы, когда метка сдвинулась.

Цена: сообщение, пришедшее при подключённом по BLE приложении и не забранное им до
перезагрузки узла, после перезагрузки не вернётся.

## Ограничения

- USB-сборки nRF52: `isConnected()` у проводного линка всегда истинно, поэтому
  запись помечается текущим сеансом, даже если к порту никто не подключён. Маршрут
  уйдёт, как только приложение начнёт новый сеанс (`CMD_APP_START`).
- Сообщение, выброшенное из середины RAM-очереди при её переполнении, после
  перезагрузки может вернуться, если его запись ещё в кольце (метка его не
  покрывает). На практике кольцо (24) много меньше очереди (256), и такая запись
  уже перезаписана.
- Хранится только та копия, что узел принял и расшифровал, — то, как сообщение
  дошло **именно до нас**. Копии-повторы, услышанные позже через ретрансляторы, не
  хранятся: подключённое приложение видит их вживую, офлайн — нет. Если отправитель
  слышит узел напрямую, маршрут — прямой (0 хопов): официальное приложение
  показывает «директ». На SEC проверено на T114: `route: kept … type=2 route=0 hops=0`.

## Флаги

| Флаг | По умолчанию | Что делает |
|---|---|---|
| `WITH_OFFLINE_ROUTES` | 1 | маршруты канальных сообщений; `0` — только очередь |
| `OFFLINE_STORE_SLOTS` | 24 | размер кольца во флеше |
| `OFFLINE_ROUTE_POOL_SLOTS` | 6 | маршрутов в RAM до записи во флеш |
| `OFFLINE_STORE_OFF` | 0 | `1` — очередь только в RAM |
| `OFFLINE_STORE_DEBUG` | 0 | трассировка `offline: ...` в Serial; не для сборок, где Serial — протокол |

## Как проверить на железе

Сборка с `-D OFFLINE_STORE_DEBUG=1`. Каналы проверяются с каждым клиентом —
официальным приложением, meshcore-open и MCO Advanced.

1. Отключить приложение, дождаться сообщений в канал (флудом), в логе:
   `route: kept seq=… len=…`, затем `store: seq=… route=… written`.
2. Перезагрузить узел: `store: opened, N held, N restored, 0 stale, 0 lost`.
3. Подключить приложение: `route: seq=… sent` перед каждым канальным сообщением. В
   приложении:
   - официальное: у канального сообщения есть «услышанные повторы» с путём;
   - meshcore-open и MCO Advanced: у канального сообщения есть путь;
   - ни одно приложение не показывает лишний повтор у сообщений, пришедших, пока
     оно было подключено.
